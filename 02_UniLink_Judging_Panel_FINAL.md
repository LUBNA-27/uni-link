# 4. How I would change UniLink after seeing this panel

I would not change your entire idea. I would make five targeted improvements.

**1. Make accessibility impossible to ignore.** Demonstrate that an inaccessible vehicle or unverified campus path is rejected by the backend. Support keyboard navigation, screen readers, high-contrast text and spoken journey updates.

**2. Add a genuine transport comparison.** Show existing bus travel, solo ride-hailing, direct shared travel and UniLink. Compare cost, expected arrival and transfer uncertainty using clearly labeled assumptions.

**3. Make the algorithm explain itself.** Add a small expandable section showing candidate routes, rejected options and reasons. This gives transport specialists and AI engineers something meaningful to evaluate.

**4. Collect actual student evidence today.** Even a small, honestly reported convenience sample is more valuable than an impressive survey target that has not been reached.

**5. Treat the Jeeny integration as a product proposal.** Show where UniLink sits inside the existing app, how students return to it every morning and what Jeeny would need to launch a pilot.

## The demonstration for this panel (Rev. E)
Timetable → strict request → Best Deal → simulated fair-split confirmation → co-rider cancellation rescue → optional Class Shift → wheelchair/no-option → measured evidence → commercial offer.
